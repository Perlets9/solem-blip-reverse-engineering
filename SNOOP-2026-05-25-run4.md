## 1. Frequency encoding — DECODED

The program flags row (`37 0e 00 [SLOT] ...`, 12 bytes of payload) layout
is now confirmed as:

```
[?:3] [BUDGET:1] [FREQ_TYPE:1] [DOW_BITMAP:1] [PERIOD:1] [DAYS_TO_NEXT:1] [DAY:1] [MONTH:1] [YEAR:BE16]
  0     3            4               5              6           7                8       9       10..11
```

| Byte | Field | Notes |
|---|---|---|
| 0–2 | reserved | Always `00 00 00` in captures. May hide "Exclude 31st" — see §1.2. |
| 3 | `BUDGET` | Water budget %, default `0x64`=100. Range 0–200 per MySolem slider. |
| **4** | **`FREQ_TYPE`** | **Frequency mode code (see §1.1)** |
| 5 | `DOW_BITMAP` | Days-of-week bitmap. `0x7f` (all 7) when not in Custom mode. Bit ordering to be confirmed via Custom-mode capture. |
| **6** | **`PERIOD`** | **Days between firings, used when `FREQ_TYPE`=Interval/Weekly.** |
| **7** | **`DAYS_TO_NEXT`** | **Days from today until first firing.** Equivalent to encoding the start date as an offset. |
| 8 | `DAY` | Last-modified day (today on the phone) |
| 9 | `MONTH` | Last-modified month |
| 10–11 | `YEAR:BE16` | Last-modified year (e.g. `07 ea` = 2026) |

The bytes 8–11 are **NOT** the program start date — they are the
"last edited on" timestamp written by MySolem on every save (in all 4
runs the value matched the date the capture was taken).

### 1.1 Frequency type codes

From this capture:

| `FREQ_TYPE` (byte 4) | Mode | Evidence |
|---|---|---|
| `0x00` | Daily | All earlier captures when programs were "Daily" |
| `0x03` | Odd days | Program C in this run |
| `0x04` | Interval / Weekly | Programs A (Weekly) and B (Interval) — see §1.4 |
| `0x01`, `0x02`, `0x05`, `0x06`, `0x07` | TBD (Every 2 days / Every 3 days / Even days / Custom / ???) | Not in this capture |

The MySolem dialog lists 8 modes, so codes `0x00..0x07` likely cover them
all. Educated guesses (need confirmation):
- `0x01` → Every 2 days
- `0x02` → Every 3 days
- `0x05` → Even days (mirror of Odd)
- `0x06` → Custom (uses `DOW_BITMAP`)
- `0x07` → Interval if separate from Weekly, or unused

### 1.2 The "Exclude 31st" toggle for Odd days — UNKNOWN

The Program C screenshot has **Exclude 31st = ON**, but every "unknown"
byte we've identified (`bytes 0..2`, the trailing program rows, the `2f 12
01` reserved row) is all-zero in the capture. The toggle is therefore
either:

1. Encoded in a bit position we haven't isolated yet (within the same
   flags row).
2. Stored only on the phone (the firmware always applies "exclude 31"
   in Odd-days mode).

Compare-with-toggle-off capture would settle this.

### 1.3 `DAYS_TO_NEXT` field — strong evidence

Today (capture date) is **Monday, 25 May 2026**.

| Program | FREQ | Start date in app | DAYS_TO_NEXT (byte 7) | Today + N = matches start date? |
|---|---|---|---|---|
| A | Weekly | Wed 27 May 2026 | `0x02` = 2 | 25 + 2 = 27 ✓ |
| B | Interval/4d | Thu 28 May 2026 | `0x03` = 3 | 25 + 3 = 28 ✓ |
| C | Odd days | — (no start times) | `0x00` = 0 | 25 is odd → fires today ✓ |

Three out of three. **Confident**: byte 7 is the number of days from
the save date until the first firing. The firmware likely re-derives the
day-of-week / next-firing on every boot using this offset + `DAY/MONTH/YEAR`.

### 1.4 Weekly vs "Interval / every 7 days"

Program A (Weekly): `FREQ_TYPE=4, PERIOD=7`
Program B (Interval / 4 days): `FREQ_TYPE=4, PERIOD=4`

So **"Weekly" in MySolem is just `FREQ_TYPE=4` with `PERIOD=7`**. MySolem
shows the friendlier label "Weekly" when period happens to be 7,
"Every 2 days" when 2, "Every 3 days" when 3, and "Interval" when the
user picked an arbitrary period.

This matches the 8-entry dropdown: Daily / Every 2 / Every 3 / Weekly /
Even / Odd / Custom / Interval — four of them collapse into the same
firmware code (`FREQ_TYPE=4` with different `PERIOD`).
