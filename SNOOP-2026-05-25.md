# MySolem BLE Snoop Analysis — 2026-05-25

Raw analysis of the Android Bluetooth HCI snoop log captured while operating
the MySolem app against a `BL2IP-D5AA7E` controller.

> Source log: `temp2/report/FS/data/log/bt/btsnoop_hci.log` (3.5 MB, BTSnoop
> v1, HCI UART H4).
> 178 frames on the SOLEM service (handle `0x000e` notify, `0x0011` write).
> Captured: 2026-05-25 ~15:55.

## 1. ATT handles in use

| Handle | Direction | UUID | Description |
|---|---|---|---|
| `0x000e` | Notify (`0x1b`) | `108b0003-...` | Device → app responses |
| `0x0011` | Write-without-response (`0x52`) | `108b0002-...` | App → device commands |

Same as in `DISCOVERY.md`; handles are stable, no change.

## 2. Frame format (general)

Both writes and notifications follow:

```
[OPCODE:1] [LEN:1] [PAYLOAD:LEN]
```

with `LEN` matching the number of payload bytes that follow. Responses use
`OPCODE = REQUEST_OPCODE + 1` (e.g. `0x2f` write → `0x30` notify, `0x3f` write
→ `0x40` notify, `0x3b` write → `0x3c` notify).

Some responses for status (`0x3b`) use the larger frame format prefixed by
`32 10` / `3c 10` followed by a 1-byte packet index (`02`, `01`, `00`) — this
is the legacy 3-packet status response already known from `DISCOVERY.md`.

### 3.5 Read program data (t ≈ 32.20s) — THE BIG ONE

`WR 39 00` → device dumps the configuration of **all 12 program slots** as
84 frames (7 records per slot × 12 slots), with response opcode `0x3a`.

Record structure (per program slot):

```
3a 12 <SEQ> <SLOT> 50 72 6f 67 72 61 6d 20 <X>00...    ← "Program X" (16-char name)
3a 12 <SEQ> <SLOT> 00 00 00 00 ...                     ← (zeros / reserved)
3a 0e <SEQ> <SLOT> 00 00 00 64 00 7f 00 00 19 05 07 ea ← flags+date
3a 12 <SEQ> <SLOT> 01 f4 05 a0 05 a0 ...               ← 8× per-station durations (BE16 seconds)
3a 11 <SEQ> <SLOT> 00 05 64 00 00 ...                  ← station→program mapping?
3a 11 <SEQ> <SLOT> 00 00 ...                           ← (zeros / reserved)
3a 08 <SEQ> <SLOT> 00 00 00 00 00 00 00                ← short final record
```

Where `<SLOT>` is the program slot index (`0x10..0x1b` = 12 slots) and
`<SEQ>` is a global counter that ticks down across the whole dump.

#### Program A (slot `0x10`) captured

| Record | Payload |
|---|---|
| name | `"Program A"` (`50 72 6f 67 72 61 6d 20 41 00 00 00 00 00 00 00`) |
| flags | `00 00 00 64 00 7f 00 00 19 05 07 ea` → budget=`64`=100, days=`7f`=all 7, date=25/05/2026 |
| durations | `01 f4 05 a0 05 a0 05 a0 05 a0 05 a0 05 a0 05 a0` → `0x01f4`=500s + 7×`0x05a0`=1440s (24min). First slot may be header. |
| extra | `00 05 64 00 00 00 ...` |

#### Program B (slot `0x11`) captured

| Record | Payload |
|---|---|
| name | `"Program B"` |
| flags | `00 00 00 64 00 7f 00 00 19 05 07 ea` (same: budget 100%, all 7 days) |
| durations | `02 12 05 a0 05 a0 05 a0 05 a0 05 a0 05 a0 05 a0` |
| extra | `00 00 00 00 05 64 00 00 ...` |

#### Program C and beyond (slots `0x12..0x1b`)

All-zero payloads. **MySolem exposes only 3 programs in the UI, but the
firmware reserves 12 slots**. Slots 12+ are empty / unused.

#### Date encoding

`19 05 07 ea` = `0x19`=25 day, `0x05`=5 month, `0x07ea`=2026 year (big-endian).

#### Days-of-week bitmap

`0x7f` = `0b01111111` = all 7 days enabled. Bit positions for Mon..Sun TBD.

### 3.7 Write programs (t ≈ 65.11s)

The user saved a configuration change. Sequence:

```
WR 3f 11 00 02 00 00 64 00 64 00 64 00 64 00 64 00 64 00 64 00 64  ← write monthly budget (record 01)
NF 40 11 ...   (echo)
WR 3f 10 01 00 64 00 64 00 64 00 64 00 64 00 64 ff ff ff ff ff      ← write monthly budget (record 00)
NF 40 10 ...   (echo with corrected sentinels)

WR 2f 12 00 10 "Program A"...      ← write program A name
NF 30 12 ...   (echo)
WR 2f 12 01 10 00...               ← record 01 of program A
NF 30 12 ...
WR 37 0e 00 10 00 00 00 64 00 7f 00 00 19 05 07 ea  ← flags+date P-A
NF 38 0e ...
WR 37 12 01 10 01 b8 05 a0 ...     ← durations P-A (note: 01 b8 = 440, vs read 01 f4 = 500 — user changed it!)
NF 38 12 ...
WR 37 11 02 10 00 05 64 00 ...     ← extra P-A
WR 37 11 03 10 00 ...
WR 37 08 04 10 00...               ← final P-A record

(same flow for Program B with slot 0x11)

WR 3b 00                            ← FINAL COMMIT (returns status)
NF 3c 10 02 40 ...                  ← status idle, packet 1/3
NF 3c 10 01 ...                     ← packet 2/3
NF 3c 10 00 ...                     ← packet 3/3
```

**Write opcodes**: `0x2f` (program name), `0x37` (program data row), `0x3f`
(water budget), `0x3b` (commit).
**Response opcodes** = request + 1.

## 4. Battery hypothesis — needs more data

### 4.1 Observation

Bytes 10–11 of status packet 1 change across captures:

| Capture date | Bytes 10–11 | Notes |
|---|---|---|
| 2025-08 (DISCOVERY-LOGS.txt) | `58 14` | Original RE — battery state unknown |
| 2026-05-25 (this log) | `4d 17` | ~9 months later, same controller? |

Byte 10: `0x58`=88 → `0x4d`=77 (decreased by 11 in 9 months).
Byte 11: `0x14`=20 → `0x17`=23 (increased by 3).

If byte 10 is **battery percentage**: 88% → 77% over 9 months on a 9V battery
is plausible.
If bytes 10–11 are a BE16 **voltage in millivolts**: `0x5814`=22548 mV (way
too high) — unlikely.
If `0x14 58` LE16 = 5208 mV → too low for 9V battery.

**Working hypothesis**: byte 10 = battery percentage, byte 11 = some
secondary metric (temperature? capacity calibration?).

Also, byte 3 of the date-sync frame (`03 06 00 [7e] 05 19 0f 1d 0d`) had
value `0x7e`=126 — could also be battery-related, but a single sample.

### 4.2 How to confirm

Track byte 10 across time, ideally with one of:
- Power the controller with a bench supply and step voltage from 9V → 6V,
  watching the byte change.
- Long-running HA sensor: log byte 10 daily for weeks and correlate with
  app-reported battery.

| `0xf7` | `0xf8` | read | Flags / unknown | 3 bytes |
