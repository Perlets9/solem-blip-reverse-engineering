# MySolem BLE Snoop Analysis — 2026-05-25 (run 2)

Second capture against the same `BL2IP-D5AA7E` controller, ~15 minutes after
[run 1](./SNOOP-2026-05-25.md).

> Source log: `temp2/report2/FS/data/log/bt/btsnoop_hci.log` (2.4 MB).
> 160 frames on the SOLEM service.
> Captured user actions:
> - **Manually launched Program B** from the MySolem app
> - **Added start time `06:00`** to Program A (previously only `07:20`)

The handshake (opcodes `0x0f`, `0xe3`, `0xf7`, `0x3b`, `0x03`, `0x41`, `0x39`,
`0x35`) is identical to run 1. New / changed traffic is documented below.

## 1. "Run program" command — DECODED

```
t=44.89 WR 31 05 14 02 00 00 00   ← Run Program B
t=44.91 WR 3b 00                   ← Commit + status refresh
```

→ **`31 05 14 [N] 00 00 00`** where `N` is the 1-indexed program number
(1=Program A, 2=Program B, 3=Program C).

This exactly matches the speculative note in `hacking/solem.py`:
- `31051400010000 dimi seara` → Run Program 1
- `31051400020000 avarie` → Run Program 2

The device responds with a normal status (mode `0x42` single station active
or `0x41` all stations, depending on what the program is doing).

After ~25 seconds the user stopped the run with the existing stop command:
```
t=69.30 WR 31 05 15 00 ff 00 00    ← Stop
```

## 2. Start times — DECODED (different from where we thought!)

The schedule read `0x35`/`0x36` was still all zeros despite the user having
1 start time set (`07:20`) at the start of the session. So **start times
are NOT stored in the schedule records** — they live inside the **program
data records** read via `0x39`.

Specifically, the row read at `slot 0x01` of a program (response sub-row
`50` for Program A, `49` for Program B in run 2) contains:

```
[ ST1:BE16 ] [ ST2:BE16 ] [ FILL:BE16 ] × 6   (16 bytes total = 8 × BE16)
```

Where:
- `STk:BE16` = start time `k`, encoded as **minutes since midnight**.
  e.g. `0x0168` = 360 = 06:00, `0x01b8` = 440 = 07:20.
- `FILL:BE16` = `0x05a0` (1440 = 24 hours / 24 min — sentinel for "unused
  slot").

### Evidence

| Capture | Program A row 01 | Decoded |
|---|---|---|
| run 1 read | `01f4 05a0 05a0 05a0 05a0 05a0 05a0 05a0` | 1 start time at `0x01f4`=500=08:20, 7 fillers |
| run 1 write | `01b8 05a0 05a0 05a0 05a0 05a0 05a0 05a0` | user changed start time → 07:20 |
| run 2 read | `01b8 05a0 05a0 05a0 05a0 05a0 05a0 05a0` | confirms previous write was persisted |
| run 2 write | `0168 01b8 05a0 05a0 05a0 05a0 05a0 05a0` | **added 06:00** (`0x0168`=360) BEFORE the existing 07:20 |

This is consistent with the MySolem screenshot showing "Start time 1: 06:00,
Start time 2: 07:20" after the second session.

**Max 8 start times per program** (limited by the slot size). MySolem may
enforce a smaller cap visually.

## 3. Per-station durations — partially decoded

The row at `slot 0x02` of a program (response sub-row `4f` for Program A,
`48` for Program B) appears to encode per-station durations:

| Program | row 02 payload (16 bytes) |
|---|---|
| A (slot `0x10`) | `00 05 64 00 00 00 00 00 00 00 00 00 00 00 00 00` |
| B (slot `0x11`) | `00 00 00 05 64 00 00 00 00 00 00 00 00 00 00 00` |

The same value `05 64` (=`0x0564`=1380s=23min) appears at byte offset 1–2 in
Program A and at offset 3–4 in Program B. **Hypothesis**: this is a list of
station entries where each station has its program-specific watering
duration; the position in the array tells you which station, and the value
is the duration in BE16 seconds. The pattern of shifts matches a layout of
3-byte records per station, but more captures (with different stations
mapped to different programs) are needed to confirm the exact field
boundaries.

## 4. Date/time sync — second sample

| Capture | Date-sync write | Decoded |
|---|---|---|
| run 1 | `03 06 00 7e 05 19 0f 1d 0d` | 25/05 15:29:13, byte 3 = `0x7e` |
| run 2 | `03 06 00 7e 05 19 10 08 22` | 25/05 16:08:34, byte 3 = `0x7e` |

Byte `0x7e` is **the same across both sessions**. This weakens (but does
not exclude) the battery hypothesis for that byte — could be a constant
firmware-version-related marker. The dynamic byte for battery remains
status packet 1 byte 10 (`0x4d` in both runs — same value, makes sense
they're 15 minutes apart on the same battery).

## 5. Status packet 1, run 2

Bytes 10–11 of status packet 1 in run 2 are **`4d 17`** — same as run 1.
The two captures are 15 minutes apart, so an unchanged byte is expected if
this is the battery level. To confirm, we'd want a capture days/weeks later.

## 6. Open question: the "Security key" feature

The MySolem "Information" screen exposes a **Security key** option (see
screenshot supplied 2026-05-25). The user has not configured one. This is
likely an application-level authentication separate from BLE pairing
(possibly a small write that must precede control commands when set).
Since the user does not need it, we leave it unmapped for now — but we
should be aware that an enabled Security key could break the integration
unless we support it.

## 7. Confirmed opcodes (consolidated)

Updated table with the new findings:

| Bytes | Direction | Purpose | Status |
|---|---|---|---|
| `31 05 14 [N] 00 00 00` | write | **Run program N** (1..3) | ✅ Confirmed |
| `31 05 12 [STN] 00 [SEC:BE16]` | write | Start station for SEC seconds | ✅ Confirmed |
| `31 05 11 00 00 [SEC:BE16]` | write | Start all stations | ✅ Confirmed |
| `31 05 15 00 ff 00 00` | write | Stop | ✅ Confirmed |
| `3b 00` | write | Status read (3-packet response) | ✅ Confirmed |

Reads (no payload, fixed responses):

| Bytes | Returns |
|---|---|
| `0f 00` | Device info (MAC + name) — 2 frames |
| `e3 00` | Extended ID — 1 frame |
| `f7 00` | Flags (3 zero bytes) |
| `41 00` | Monthly water budget — 2 frames × 12 months |
| `39 00` | Programs — 84 frames (12 slots × 7 rows) |
| `35 00` | Schedule — 24 frames, **purpose still unknown** (always zero so far) |

Writes (program save):

| Opcode | Purpose |
|---|---|
| `2f 12 [ROW] [SLOT] ...` | Program name (`ROW=00`) / reserved (`ROW=01`) |
| `37 0e [00] [SLOT] [BUDGET] [DAYS] ... [DATE]` | Program flags |
| `37 12 [01] [SLOT] [start_times + fillers]` | Start times row |
| `37 11 [02|03] [SLOT] ...` | Station-duration rows |
| `37 08 [04] [SLOT] ...` | Final program row |
| `3f [11|10] [01|00] ...` | Monthly water budget rows |
| `3b 00` | Final commit (always last in a write batch) |
